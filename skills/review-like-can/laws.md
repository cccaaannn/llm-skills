# Can's laws of LLMs
- Human-maintained list, do not edit.
- This list is designed to build and maintain codebases in LLM and human collaborative environments.
- After implementing a feature recheck the rules and fix any violations, even if the code works, it is not good enough for us.

0. "Quality is built in, not bolted on" The end result of our application is good only because the inner parts reflect the same quality, we care about the line by line code quality. Nothing is less important, everything matters.
1. "Make the incorrect state unrepresentable" this is how we write code, how we design APIs, how we decide on function parameters, how we put together classes, the code we write can never be misused, it can never be in a state that is incorrect. If something can be incorrect it will be at some point, we do not allow this.
   - Example: A method to create a user with username, mail and password, for some users username is "null" because they don't have username. A better designed version takes an inherited user object that does not have a username field, so the API is self-describing and impossible to misuse.  
2. "Explicit is better than implicit" This is literally for everything, for every code concept we always use explicit names no exceptions, structure, methods, variables. We never want to guess what something is doing, it has to tell us. This will also help future-proof the name, we don't want to change names later so find a good one from the start.
   - Example: If a get method is mutating something internally let it tell it, like "updateAndGetXXX" instead of "getXXX". Or a bare "Subscription" is likely to collide with many library classes, let it tell what subscription it is. Add suffixes or prefixes, make it longer until it describes what it is.
   1. Never mutate objects implicitly in functions or hide mutations in any way, always return the changed variable explicitly as result or as that language's convention.
   2. Do not nest function calls, have explicit variables with names that describe each step, a pile of nested 1 liner does the same thing but takes 10 times more to understand.
   3. Do not write mutation in a condition checking block, a mutation should happen before the "if" then the result should be checked, not at the same time.
3. "Simple is better than complex" Functions MUST have few parameters, if a function has more than 3 parameters it is a smell we should consider refactoring it. A function with more than 5 parameters should be refactored and if it can't it has to be justified by the user. Mitigating this with class variables is not a solution it makes the function less pure and more stateful, which is a larger problem. Or simply putting all variables to a class and passing that around is not a perfect solution either, if there are too many parameters it means that function is possibly doing too much, this needs to be solved structurally not mechanically. (There are cases that it is ok to pass variables with an "options" or "settings" class to reduce variables but needs to be justified as a pile of flags or a mapping etc. never logic carrying 5+ parameters).
   - Example: A function that takes 5 parameters, we split the work and have a parent method call them with their descriptive names.
   1. We don't like using "else" or "else if" clauses, prefer early returns and avoid all possible nesting.
   2. Do not sacrifice simplicity for testing, it is better to have a testable structure, if testing needs application code changes user decides it. We don't create more surface for testing just to test it.
4. "State is evil" Aim for as little state as possible in general, if something can be pure we make it pure, if something can be immutable we make it immutable, if something can be final/constant we make it final/constant. Less state means fewer and less complicated bugs. On a larger scale, let the user know of the new state and possible downsides, like the impacts of HA setups, limitations with restarts, problems with synchronization, performance tradeoffs etc. Assume that you don't know the full picture but user does.
   - Example: A simple parser method in a class, if it can be done without a class/internal variable we extract it to be pure. Or we add a long-lived variable to a class and it causes a possible cluster inconsistency, user needs to know that.
5. "Comments lie, code can't" Code should document itself, with explicit variable and function names we almost never need comments, do NOT use comments to describe the code. If we need to describe the code it is a sign that there is a problem. Any remaining comment should be explaining the "why" rather than "what" or "how".
   - Example: Suppose we have variable "user" and comment "holds current active user", comment is only in one place, it can be missed and variable can be renamed and drift from the comment, better option is to have the name like this "activeUser". 
6. "'Nothing' is wrong" We are extremely sensitive about nulls or empty values, null should not be treated as a valid value because it is not. If by any chance something can be null we mark it.
   - Example: A validation function returns null for invalid input, better option is to return a Result/Optional type that can be empty or have a value, so the caller has to check it.
7. "Consistency matters" We always follow codebase conventions, before designing anything always check if there is a similar pattern in the codebase and follow it. To the point that the order of variables on similar classes or their names, their prefixes, orders of methods, the way we do string concatenation, how we log errors, which language conventions are commonplace etc. all should be consistent.
   - Example: If we have a class that has a variable called "userId" we should not use "userID". Or if we have a method that is called "getUser" we should not use "fetchUser".
   1. Do not invent important names for concepts, if we need a new word during the implementation clarify it with user. Names are how we understand features, they matter.
8. "There is no magic, only code" We do not use magic numbers or bare strings for things that can be enums or shared constants, it makes refactoring scary. Any bare string has to be justified to be left in the code. Always use strongly typed values, no unclear types like "Object", "any" etc. We want compiler safety on everything we write.
   - Example: We have an input that we need to serialize to JSON, we prefer a static object instead of a mapping with bare string keys. Or there is a constant number that needs to be used in multiple places, we extract it to a constant class and use it from there.
9. "Together but not tangled" Always try to solve synchronization problems with structure first, rather than using synchronization primitives. If there is nothing to synchronize there is no chance to have a race. We never tolerate errors due to concurrency, they are hard to test and even harder to trace. Avoiding them is the best way.
   - Example: Try to use callbacks instead of adding locks, semaphores or volatile. Or reduce the part that is going to be mutated to shrink the critical section and decrease the amount of locks needed.
10. "OOP is not enough" We use the known programming concepts like SOLID. "L" and "I" are particularly important, interfaces should represent what the implementors are, and implementors should implement the whole interface properly. If they can't, then either the interface is too wide or the implementors are not valid. We prefer composition over inheritance, larger object hierarchies make later changes more difficult, inheritance should be used with caution. Never hesitate to copy a "data class", but never copy something to share logic. 
    - Example: If you have a "UserProvider" and only some providers can implement certain methods either the interface is too wide or some of the implementers are not valid providers. Or a piece of a class needs to be reused, we extract the logic to its own class and compose it with the original place and the new place. 
11. "Not the symptom but the disease" We do things the "right" way, not the "fast" way. When solving problems, adding more parameters to functions or adding more overloads as a solution is not a good way, this is a patch. Always try to solve the problem itself not patch it. This might require some structural change, always recommend a better solution to the user if you can see one, it could be breaking existing call-sites or could be risky but user decides this not you.
    - Example: A userCreate(name,role) function now needs an isAdmin parameter, maybe role should be absorbing this? Or there are incompatible dependencies and force install solves this, not a good idea, it is not a solution, we need to solve the dependency problem itself.
12. "One broken window is enough" Tests should never fail, occasional failures cause us to ignore the tests which kills the purpose of the tests.
    - Example: There can be timing dependent tests, we need a common infra for them to always have enough time, and on different environments we let them have different timeouts so there are no "sometimes works" tests.
